# Pregenerated VR Experience Workflow

The original VR pipeline generated assets live, inside Unreal, when a designer clicked a Blueprint node — meaning "start experience" meant "start generating, then wait" (OpenAI image call + PNG→HDR conversion + ElevenLabs calls + ffmpeg conversion, all synchronous/blocking on the editor thread for the panorama step).

This workflow moves generation earlier: the web app generates the VR assets ahead of time and writes them to fixed, overwrite-in-place paths. Unreal's job at "start" time becomes a synchronous local file import with no network calls — effectively instant.

## Web app: `/generate-vr-experience`

`Conversation/local_server.py` exposes a new POST endpoint alongside `/generate-2d-experience`. It takes the *un-flattened* prompts (specifically `prompt1_environment_360`, not the flattened 2D image prompt) and:

1. Calls the OpenAI Images API and saves the panorama PNG.
2. Converts PNG → HDR in-process, by loading `Scripts/png_to_hdr.py` directly as a module (no subprocess) — the same dependency-free converter the C++ side shells out to.
3. Calls a sound-effect provider (skipped if the prompt is `"none"`) — see "Sound effect provider" below — then converts the result to WAV via `ffmpeg` (mono 48kHz 16-bit) regardless of which provider produced it. **No `loudnorm` normalization or gain is applied** — the earlier VR "杂音"/noise reports traced back to the C++ path's `loudnorm` filter amplifying the underlying noise floor, so this path intentionally stays as close to the raw generated audio as possible.
4. Archives a copy of everything into `record/<timestamp>/VR/` (same mechanism as the rest of the [generation record archive](GenerationRecordWorkflow.md)) — timestamp-keyed history is preserved even though the "live" copy at the fixed path gets overwritten every run.

### Sound effect provider

The web UI's Settings drawer has a "音效生成使用" / "Sound Effect Provider" dropdown (`ElevenLabs` or `fal.ai (Stable Audio)`), plus a `fal.ai API Key` field next to the ElevenLabs one. Both `/generate-2d-experience` and `/generate-vr-experience` accept `sound_provider` (`"elevenlabs"` | `"falai"`) and `fal_api_key` in the request body and dispatch accordingly:

- **ElevenLabs** (default): `generate_elevenlabs_sound()` — unchanged, `POST api.elevenlabs.io/v1/sound-generation`, returns mp3.
- **fal.ai**: `generate_falai_sound()` — `fal-ai/stable-audio`'s queue API (`POST queue.fal.run/fal-ai/stable-audio` submit → poll `.../requests/{id}/status` until `COMPLETED` → `GET .../requests/{id}` for `audio_file.url` → download). Returns WAV. Auth is `Authorization: Key <fal_api_key>`; the final CDN download itself is unauthenticated (presigned URL — adding the auth header there can break the signature). `seconds_total` is clamped to fal's 0-47s limit.

Only the sound effect is switchable — image generation always uses OpenAI, and music generation is disabled for both providers (see below). The C++ `ElevenLabsSoundEffectGenerator` Blueprint node (live in-editor generation, independent of the web app) is untouched and still ElevenLabs-only.

**Music generation is currently disabled** (ElevenLabs credit cost) in both `/generate-2d-experience` and `/generate-vr-experience`. `generate_elevenlabs_music()` is still defined in `local_server.py`, just not called, so re-enabling it later is a small, localized change rather than a rewrite. `prompt3_music` is still generated by the OpenAI conversation agent and written into `generated_prompt.json` — only the ElevenLabs music call itself is skipped.

### Fixed output paths

Every run overwrites the same files — there is deliberately no per-timestamp naming here, so the Blueprint import node below never needs its path inputs touched:

| Asset | Path |
|---|---|
| Panorama PNG | `Saved/AI360/VRExperiencePanorama.png` |
| Panorama HDR | `Saved/AI360/VRExperiencePanorama.hdr` |
| Sound effect WAV | `Saved/AISFX/VRExperienceSFX.wav` (source mp3 kept alongside as `.source.mp3`) |
| Music WAV | `Saved/AIMusic/VRExperienceMusic.wav` — not currently written (music generation disabled, see above) |

These are separate from `GeneratedPanorama` / `GeneratedSFX` / `GeneratedMusic`, the default filenames the original live-generation Blueprint nodes (`Generate 360 HDRI From Prompt`, etc.) still use — so a designer generating directly from inside Unreal, bypassing the web app entirely, doesn't collide with the web-pregenerated set.

## Web UI

The confirm screen has a new "生成VR体验" / "Generate VR Experience" button next to the existing 2D one (`app.js`: `generateVrExperience()`). It reuses `state.output.result.prompt1_environment_360` as-is (not the flattened 2D variant) and the same `buildElevenLabsSoundPrompt()` noise-guard wrapping already used for the 2D sound effect. Status is shown inline; there's no in-browser playback for this button specifically, but the resulting files are immediately visible under the VR side of [the record review page](GenerationRecordWorkflow.md#review-page) since they get archived too.

## Unreal side: `Import Pregenerated VR Experience`

`Source/vrst/PregeneratedVRImporter.cpp` adds one synchronous `UBlueprintFunctionLibrary` node, `Import Pregenerated VR Experience`. For each of panorama/SFX/music, if the fixed-path file exists it runs a synchronous `UAssetImportTask` (same import mechanism the live generator nodes use) into `/Game/AI360`, `/Game/AISFX`, `/Game/AIMusic`; if it's missing, that asset is silently skipped rather than treated as an error (mirrors the 2D path, where sound/music are optional). No HTTP calls, no `png_to_hdr.py`, no `ffmpeg` — everything on this node is local disk I/O plus the asset import.

Wire this into whatever "start experience" trigger exists in the level/widget Blueprint: as long as the web app generated the assets first, clicking it imports and is playable essentially immediately.

`bMarkSoundAndMusicLooping` (default `true`) marks the imported SFX/Music `SoundWave`s as looping, matching the behavior the live nodes get when their `Loop`/`Loop In Unreal` input is checked.
